## 리랭커가 정말 더 나은 장소를 고르는지 확인하고 싶었다
{: #goal }

TravelMate의 장소 검색은 BGE-M3 임베딩으로 후보 30개를 찾고, BGE 리랭커가 질문과 장소 설명을 한 쌍씩 다시 읽어 순서를 정한다. 리랭커를 거치면 응답이 느려지므로, 그 비용을 감수할 만큼 결과가 좋아지는지 숫자로 확인해야 했다.

확인하고 싶은 것은 두 가지였다.

1. **찾아야 할 장소를 결과에 가져오는가.** 정답 장소가 결과에 없으면 순서를 아무리 바꿔도 의미가 없다.
2. **찾은 장소를 위로 올리는가.** 사용자는 첫 번째와 상위 몇 개 결과를 주로 본다. 리랭커가 하는 일이 순서를 바꾸는 것이므로 순위를 직접 평가해야 한다.

둘 다 재려면 질문마다 어느 장소가 정답인지 미리 정해 둔 골든 데이터셋이 먼저 필요했다.

## 골든 데이터셋을 CSV로 만들었다
{: #golden-dataset }

### 장소 원문을 스냅샷으로 고정했다

정답의 근거가 되는 장소 설명이 평가 도중 바뀌면 같은 질문의 정답도 흔들린다. 그래서 DB의 서울 관광지 449건과 TourAPI 원본 449건을 `snapshot.json` 한 파일로 내보내고 SHA-256 해시로 고정했다. 이후 모든 판정 근거는 이 스냅샷의 문장을 그대로 인용했다.

### 주제마다 질문 유형을 나눠 100문항을 만들었다

궁궐, 성당, 수족관, 습지, 철도 유산, 공예 체험처럼 20개 주제를 정하고 주제마다 질문 5개를 만들었다. 한 주제 안에 질문 유형을 섞어 검색이 어떤 상황에서 약한지 나눠 볼 수 있게 했다.

| 질문 유형 | 문항 | 예시 |
| --- | ---: | --- |
| 장소명 검색 | 20 | 창경궁을 찾아줘. |
| 설명으로 찾기 | 20 | 고종이 왕이 되기 전에 태어나서 자랐고 흥선대원군 가족이 살던 집을 보고 싶어. |
| 정답이 여러 개 | 20 | 종로에서 조선 왕실 가족이 생활했던 궁이나 거처를 둘러보고 싶어. |
| 대화·제외 조건 | 20 | 방금 본 곳은 빼고, 단청 없이 소박하게 지은 왕실 거처를 더 찾아줘. |
| 근거 부족 | 10 | 오늘 창경궁 야간 관람 표가 지금 몇 장 남았어? |
| 되물어야 함 | 10 | 아까 얘기한 그 성당 근처로 찾아줘. |

앞의 세 유형 60문항은 검색 API에 지역·도시·분류 조건만 넣어 바로 채점한다. 대화·제외 조건 20문항은 이전 대화와 제외할 장소를 함께 넘겨야 하고, 나머지 20문항은 장소를 고르는 대신 확인할 수 없다고 답하거나 되묻는 행동을 본다. 20개 주제 가운데 16개는 개발용(80문항), 4개는 시험용(20문항)으로 나눴다.

### 질문–장소 한 쌍을 CSV 한 행으로 판정했다

판정은 질문과 장소 한 쌍마다 0~3점을 매기는 방식으로 했다. 273행을 처음부터 손으로 채우기는 어려워서, 점수 기준과 판정 예시를 프롬프트에 넣은 퓨샷(few-shot) 방식으로 LLM에게 점수·이유·근거 문장의 초안을 만들게 했다. 그 초안을 원문과 하나씩 대조하며 직접 검수했고, 이 과정에서 약 10건의 점수를 고쳐 최종 점수를 확정했다.

| 점수 | 기준 |
| ---: | --- |
| 3 | 질문의 핵심 의도와 명시한 조건을 원문 근거로 직접 충족한다. |
| 2 | 조건을 모두 충족하지만 직접성이 낮은 유효한 대안이다. |
| 1 | 주제만 일부 맞거나 필수 조건의 근거가 없다. 정답으로 세지 않는다. |
| 0 | 다른 장소이거나 지역·제외 같은 명시 조건을 어긴다. |

2점 이상을 정답으로 보고, 3점만 모은 엄격한 정답 목록도 따로 만들었다. 검수표 CSV는 한 행이 질문 하나와 장소 하나의 판정이다. 100문항에서 273행이 나왔고, 판정한 장소는 72곳이다. 열은 다음 16개로 구성했다.

| 열 | 내용 | 예시 |
| --- | --- | --- |
| `case_id` | 주제와 번호로 만든 문항 ID | `TM-palaces-02` |
| `split` | 개발용·시험용 구분 | `development` |
| `evaluation_track` | 연결할 평가 방식 | `search_api`, `context_search`, `answer_behavior` |
| `query` | 사용자 질문 | 창경궁을 찾아줘. |
| `conditions` | 검색 API에 넘길 지역·도시·분류·제외 장소·이전 대화(JSON) | `{"region": "서울", "city": "종로", …}` |
| `semantic_constraints` | 질문에 담긴 필수 조건(JSON) | 완성품을 가져갈 수 있어야 한다 |
| `answerability` | 장소로 답할 수 있는 질문인지 | `answerable`, `insufficient_evidence`, `clarification_required` |
| `place_id`, `place_name` | 판정한 장소 | `208`, 서울 운현궁 |
| `relevance` | 0~3점 관련도 | `3` |
| `semantic_constraint_support` | 그 장소의 원문이 필수 조건을 뒷받침하는지 | `supported`, `not_supported` |
| `rationale_or_expected_behavior` | 점수를 준 이유. 장소 없이 답해야 하는 문항은 기대하는 답변 행동 | 실시간 재고를 확인할 수 없다고 밝히고 공식 예매처 확인을 안내한다. |
| `evidence` | 판정 근거가 된 스냅샷 원문 인용 | 흥선대원군의 일가가 거주하고 생활한 사저였으며, … |
| `review_status`, `human_reviewer`, `review_notes` | 검수 상태, 검수자, 검수 메모 | `human_reviewed` |

아래는 설명으로 찾기 문항의 실제 행에서 주요 열만 옮긴 것이다. `evidence`에는 판정 근거가 된 원문 문장을 스냅샷에서 그대로 복사했다.

### 판정 원본에서 평가용 JSONL을 만들었다

판정 원본을 고치면 빌드 스크립트가 검수용 CSV와 평가용 JSONL을 함께 다시 만든다. 평가 실행기는 JSONL을 읽는다. 위 문항은 JSONL에서 다음과 같은 모양이 된다(일부 필드).

```json
{
  "case_id": "TM-palaces-02",
  "split": "development",
  "case_type": "semantic",
  "query": "고종이 왕이 되기 전에 태어나서 자랐고 흥선대원군 가족이 살던 집을 보고 싶어.",
  "conditions": {"region": "서울", "city": null, "category": null, "area": null, "exclude_place_ids": [], "conversation": []},
  "relevance_threshold": 2,
  "relevant_place_ids": [208],
  "strict_relevant_place_ids": [208],
  "judgments": [
    {
      "place_id": 208,
      "name": "서울 운현궁",
      "relevance": 3,
      "evidence": [
        {
          "field": "description",
          "quote": "흥선대원군의 일가가 거주하고 생활한 사저였으며, 고종이 임금이 되기 전까지 태어나고 자란 곳이다.",
          "char_start": 67,
          "char_end": 121,
          "json_pointer": "/places/207/description"
        }
      ]
    },
    {"place_id": 378, "name": "창경궁", "relevance": 1},
    {"place_id": 380, "name": "창덕궁 낙선재", "relevance": 0}
  ],
  "unjudged_policy": "unjudged_is_not_irrelevant"

```

빌드할 때는 다음을 함께 검사한다.

- 장소 ID·이름·TourAPI ID가 스냅샷과 일치하는가
- 인용 문장이 스냅샷의 해당 위치(`json_pointer`, `char_start`~`char_end`)에 글자 그대로 있는가
- 정답 목록이 2점 이상 판정과 일치하는가
- 같은 주제의 질문이 개발용과 시험용에 나뉘어 들어가지 않았는가
- 원본에서 다시 만든 결과가 저장된 파일과 같은가

## 검수하며 정답을 고쳤다
{: #review }

초안을 원문과 다시 대조하는 과정에서 세 가지 문제를 찾아 고쳤다.

### 근거 없는 정답을 걸러냈다

"직접 만들어 가져갈 수 있는 공예 체험"을 묻는 문항에서 향수 공방과 도장 공방이 처음에 3점이었다. 만드는 체험은 있지만 완성품을 가져간다는 문장은 원문에 없었다. 이런 장소가 정답에 섞이면 검색기가 그 장소를 올렸을 때 근거 없이 점수를 받는다.

그래서 질문의 필수 조건을 `semantic_constraints` 열에 따로 적고, 장소마다 원문이 그 조건을 뒷받침하는지 `semantic_constraint_support` 열에 기록했다. 이 문항의 필수 조건은 다음과 같다.

```json
[{"id": "take_home_product", "description": "직접 만든 완성품을 가져가거나 나중에 받을 수 있다는 근거가 있다."}]
```

```csv
case_id,place_id,place_name,relevance,semantic_constraint_support,rationale_or_expected_behavior
TM-crafts-03,55,길상도예,3,"{""take_home_product"": ""supported""}",도자기를 직접 만들며 완성품은 약 4주 뒤 수령한다.
TM-crafts-03,427,향기억,1,"{""take_home_product"": ""not_supported""}",향료를 직접 배합해 향수를 만드는 체험은 있으나 만든 향수를 가져가거나 받는다는 원문 근거가 없어 정답에서 제외한다.
TM-crafts-03,415,필소굿캘리,1,"{""take_home_product"": ""not_supported""}",돌에 이름을 직접 새기는 체험은 있으나 완성품을 가져가거나 받는다는 원문 근거가 없어 정답에서 제외한다.
```

조건 근거가 `not_supported`인 장소에 2점 이상을 주면 빌드가 실패하도록 했다. 이 기준으로 공예 문항의 2건을 포함해 수족관, 한옥마을, 습지, 정원 등의 문항에서 모두 9건의 정답을 1점으로 내렸다.

### 빠진 정답을 채웠다

반대로 정답인데 판정 목록에 없던 장소도 있었다. 한옥마을 추천 문항에는 한옥 다섯 채를 옮겨 복원한 남산골한옥마을이, 습지 문항에는 서울창포원이 빠져 있었다. 원문 근거를 확인해 정답으로 추가했고, 판정은 236건에서 253건으로 늘었다.

### 개발용·시험용 분할 기준을 바꿨다

처음에는 같은 장소가 개발용과 시험용 양쪽에 정답으로 나오지 않도록 장소 ID 기준으로 나눴다. 그러자 시험 문항의 정답인 장소를 개발 문항에는 정답으로 넣을 수 없어, 실제 정답을 비워 두는 문항이 생겼다. 서울창포원이 그런 경우였다. 분할 기준을 질문 주제 단위로 바꿔 같은 주제의 질문만 나뉘지 않게 하고, 장소는 양쪽에 나와도 되도록 했다.

관광지 449곳을 질문마다 모두 판정할 수는 없어서, 판정하지 않은 장소는 오답으로 세지 않았다. 대신 상위 K개 중 판정된 장소의 비율(judged@K)을 함께 기록해 점수를 읽을 때 참고했다.

## RAGAS로 먼저 채점해 보았다
{: #ragas }

첫 평가에는 RAGAS의 ID 기반 Context Precision과 Context Recall을 사용했다. 검색 API가 돌려준 장소 ID 목록을 `retrieved_context_ids`에, 골든 데이터셋에서 2점 이상인 장소 ID를 `reference_context_ids`에 넣는다. LLM 판정 없이 ID만 비교하므로 같은 입력에는 항상 같은 점수가 나온다. 문항별 지표 결과는 LangSmith trace로 남겼다.

"창경궁을 찾아줘." 문항의 결과는 다음과 같았다.

| 창경궁을 찾아줘. | 의미 검색 | 리랭킹 |
| --- | --- | --- |
| 반환 순서(장소 ID) | 378, 379, 16, 50, 35, … | 378, 379, 380, 339, 16, … |
| 1위 | 창경궁 | 창경궁 |
| ID Context Precision | 0.05 | 0.05 |
| ID Context Recall | 1.0 | 1.0 |

두 가지 문제가 보였다.

- **Precision이 반환 개수에 묶인다.** 검색 API는 장소 20개를 돌려준다. 정답이 하나인 질문에서는 1위로 정확히 찾아도 1/20, 0.05가 최대다.
- **순서를 보지 않는다.** ID 지표는 결과를 집합으로 비교한다. 두 방식의 반환 순서가 달라도 같은 정답을 포함하면 점수가 같다. 리랭커가 하는 일이 바로 순서를 바꾸는 것이라, 이 지표로는 리랭킹의 효과가 드러나지 않았다.

RAGAS에는 Faithfulness나 Answer Correctness처럼 LLM이 답변 문장을 채점하는 지표도 있다. 이 지표들은 자연어 답변을 모범 답안·근거 문맥과 비교한다. 장소 검색 API의 응답은 장소 목록이므로, 검색 단계는 사람이 매긴 장소별 0~3점을 그대로 쓰는 순위 지표로 평가하기로 했다.

## 순위 지표로 다시 채점하고 LangSmith에 기록했다
{: #ranking-metrics }

순위를 직접 보는 지표를 K=5와 K=10에서 계산했다.

| 지표 | 확인하는 것 |
| --- | --- |
| Top-1 정확도 | 첫 번째 결과가 정답인가 |
| Hit@K | 상위 K개에 정답이 하나라도 있는가 |
| Recall@K | 알려진 정답 중 몇 개를 상위 K개에 넣었는가 |
| Precision@K · F1@K | 상위 K개 중 정답 비율과 Recall과의 균형 |
| MRR@K | 첫 정답이 얼마나 위에 있는가 |
| MAP@K | 여러 정답이 고르게 위에 있는가 |
| NDCG@K | 3점 장소가 2점 장소보다 위에 있는지까지 반영한 순위 품질 |

NDCG는 판정 점수를 이득(2<sup>점수</sup> − 1)으로 써서, 3점 장소가 위에 있을수록 점수가 높다. Top-1과 Hit@5·10까지 합쳐 문항마다 15개 값을 계산하고 LangSmith에 문항별로 기록했다. 검색 요청의 내부 구간 span과 같은 trace ID로 묶어, 어떤 문항의 순위가 바뀌었는지와 그 요청에서 어느 구간이 느렸는지를 같은 trace에서 볼 수 있게 했다.

2026년 10월 26일 로컬 검색 API에서 검색 API 조건만으로 표현할 수 있는 60문항을 채점했다.

| 지표 · 60문항 | 의미 검색 | 리랭킹 | 차이 |
| --- | ---: | ---: | ---: |
| Top-1 정확도 | 83.3% | 88.3% | +5.0%p |
| Hit@5 | 96.7% | 100% | +3.3%p |
| Recall@5 | 87.1% | 92.8% | +5.8%p |
| NDCG@10 | 0.850 | 0.907 | +0.056 |
| MRR@10 | 0.883 | 0.936 | +0.053 |

리랭킹으로 첫 결과가 정답으로 바뀐 문항은 7개, 정답에서 벗어난 문항은 4개였다. 차이는 정답이 여러 개인 20문항에서 더 컸다. 이 문항들의 Top-1은 65.0%에서 75.0%로, NDCG@10은 0.672에서 0.791로 올랐다.

"종로에서 조선 왕실 가족이 생활했던 궁이나 거처를 둘러보고 싶어."의 상위 3개를 보면 차이가 잘 드러난다. 굵은 글씨는 골든 데이터셋의 정답 장소다.

| 순위 | 의미 검색 | 리랭킹 |
| ---: | --- | --- |
| 1 | 종로 무계원 | **서울 운현궁** |
| 2 | 서순라길 | **창경궁** |
| 3 | **서울 운현궁** | **창덕궁 낙선재** |

품질은 올랐지만 리랭킹 검색은 평균 8초 넘게 걸렸다. 이 시간을 줄인 과정은 [리랭킹 성능 개선]({{ '/projects/travelmate/evaluation/reranking-performance/' | relative_url }})에 정리했다.
