# 입력·fallback·원격 이동 개선 수치 추이

- 정리일: 2026-09-20
- 브랜치: `fix/resolve-rubber-banding`
- 현재 기준 커밋: `d6d69221` (`fix: 플레이어 입력 배치 상세 캡처 비용 제거`)
- 범위: 원격 렌더 시간축, 호스트·게스트 입력 공급, Jump 전달, 2001 pre-tick Pump, 네트워크 상세 캡처 비용

## 결론

지금까지의 변화는 다음 다섯 줄로 요약할 수 있다.

1. 원격 캐릭터의 25cm 이상 큰 화면 이동은 대표 이동 구간에서 `37회 → 0회`로 줄었다.
2. 동일 PC 4인 부하에서 호스트 로컬 입력은 `실제 명령 51.6% / fallback 48.4%`에서 `실제 명령 100% / fallback 0%`로 바뀌었다.
3. 게스트 일반 입력은 2001 pre-tick 전달 뒤 `fallback 21.95~24.14% → 3.09~4.57%`로 줄었다.
4. Jump 첫 삽입 지각 거절은 조기 송신 뒤 `13.51% → 1.74%`, 이후 pre-tick 실행에서는 `0/65`가 됐다.
5. 정상 2001 상세 캡처를 기본 OFF로 바꾼 뒤 Profiler 환경의 입력이 있는 Pump 평균은 `4.019ms → 0.106660ms`, 직접 Diagnostics GC Alloc은 선택한 두 프레임 모두 `0B`가 됐다.

최종 확인한 두 PC 일반 빌드 2인 steady 구간에서는 게스트가 `59.986 command/s`를 생성했고 호스트가 게스트 명령을 `99.461%` 실제 소비했으며 fallback은 `0.539%`였다. 따라서 **입력 공급·삽입 경로는 2인 일반 환경에서 기준선을 확보했다.**

다만 사용자가 호스트 화면에서 본 게스트 캐릭터가 조금 덜 부드러운 현상은 별도다. 호스트가 보는 권위 게스트에는 일반 원격 캐릭터와 같은 LateUpdate 보간 계층이 확인되지 않아, 원격 표시 부드러움은 아직 완료로 판정하지 않는다.

모든 수치를 하나의 연속 A/B처럼 비교하면 안 된다.

## 1. 원격 캐릭터 렌더 시간축

### 수정 전 문제

기존 원격 보간은 snapshot의 로컬 수신 시각을 시간 폭으로 사용했다. Unity Pump가 한 프레임에 여러 snapshot을 처리하면 호스트상 2tick 간격인 상태가 로컬에서는 8~16ms 간격으로 압축됐고, 보간 계수 `t`가 최대 `3.409`까지 커져 급가속·되감기처럼 보였다.

### HostTick 시간축 적용 결과

| 지표 | 수정 전 | 수정 후 |
|---|---:|---:|
| 25cm 이상 화면 step | 37회 | 0회 |
| 대표 최대 화면 step | 73.47cm | 23.06cm / 21.32cm |
| 외삽 frame | 3/971인 관찰자 존재 | 1/887, 1/861 |
| `movingFrozen` | 7회 | 0회 |

수정 후가 더 낮은 FPS였고 같은 Pump에서 묶여 도착한 snapshot도 더 많았는데 큰 step은 사라졌다. 이 단계는 **수신 시각 압축 재생으로 생긴 급가속형 원격 러버밴딩 해결**로 판정했다.

이 수정은 입력 fallback 자체를 줄이는 변경은 아니다. 같은 비교 구간에서 Entity 4 fallback은 오히려 `14.4% → 18.5%`였는데도 큰 원격 step은 `37 → 0`이었다. 따라서 렌더 시간축 문제와 입력 공급 문제는 분리해 다뤘다.

## 2. 호스트 로컬 입력 공급

### 초기 동일 PC 4인 기준

| Entity | 실제 명령 | Held fallback | Neutral fallback | 전체 fallback |
|---:|---:|---:|---:|---:|
| 호스트 | 51.6% | 39.7% | 8.7% | 48.4% |
| 게스트 2 | 73.7% | 20.3% | 5.9% | 26.3% |
| 게스트 3 | 74.1% | 20.3% | 5.6% | 25.9% |
| 게스트 4 | 75.2% | 19.5% | 5.4% | 24.8% |

호스트 Update는 평균 31.08Hz까지 낮아졌지만 권위 시뮬레이션은 59.96Hz로 catch-up했다. 그 결과 호스트의 입력 생성보다 `FixedUpdate` 소비가 먼저 진행됐다.

### 호스트 pre-tick 적용 뒤

`Update`에서는 최신 held와 Jump/Fire edge를 보관하고, 각 권위 tick의 `ResolveTick(T)` 바로 전에 T번 로컬 명령을 만든다.

| 검증 | 결과 |
|---|---:|
| 전체 `eligibleSteps / preparedTicks` | 15,495 / 15,495 |
| 4인 구간 `eligibleSteps / preparedTicks` | 14,121 / 14,121 |
| `localFirstSubmitStale` | 0 |
| `heldMismatchTicks` | 0 |
| `avoidableNeutral` | 0 |
| 호스트 실제 명령 / fallback / Neutral | 100% / 0% / 0% |

초기 대비 호스트 실제 명령 소비는 `+48.4%p`, fallback은 `-48.4%p`, 상대 감소율로는 100%다. Jump 23건과 Fire 1건도 모두 `Captured → Attached → Consumed`로 연결됐다.

이 단계는 입력 공급 순서를 고쳤지만 호스트 프레임 정체 자체를 없애지는 않았다. 같은 실행에서 최대 프레임 정체는 월드 전환 포함 887.1ms였고, 게스트 fallback은 여전히 19.47~20.85%였다.

## 3. Jump 전달

### 원인 확인

조기 송신 전 Guest2의 반복 Jump 37건을 연결했을 때 결과는 다음과 같았다.

| 지표 | 조기 송신 전 | 조기 송신 후 |
|---|---:|---:|
| 호스트 첫 삽입 Accepted | 32/37, 86.49% | 169/172, 98.26% |
| 첫 삽입 `RejectedStale` | 5/37, 13.51% | 3/172, 1.74% |
| 지각 Jump 생성→첫 송신 대기 | 8.423~28.580ms, 평균 20.160ms | 전부 0.000ms |
| `ResolvedBeforeFirstSend` | 0 | 0 |
| 송신 invoke/await 실패 | 0/0 | 0/0 |

지각 거절률은 `-11.77%p`, 상대 약 87.1% 감소했다. 이후 2001 pre-tick 실행에서는 Jump `65/65`, 첫 Profiler 실행에서는 `131/131`, 상세 캡처 패치 후 Profiler 실행에서는 `60/60`, 두 PC 일반 실행에서는 `70/70`이 모두 첫 삽입 Accepted였다.

조기 송신은 Jump가 실제 새 불변 명령에 연결된 경우만 적용한다. Fire 단독, lead, ACK +12 상한, 3틱 backfill, fallback 규칙은 바꾸지 않았다.

## 5. Pump 병목 확인과 정상 2001 상세 캡처 제거

### 패치 전 Profiler 분석

저장된 raw에서 선택한 느린 프레임과 보통 프레임 모두 Pump 직속 Diagnostics가 대부분을 차지했다.

| 구분 | Pump | 직접 Diagnostics | Pump 중 Diagnostics | Diagnostics GC Alloc |
|---|---:|---:|---:|---:|
| 느린 프레임 2209 | 23.2457ms, 5 calls | 22.8414ms | 98.26% | 161,303B |
| 보통 프레임 2540 | 5.2627ms, 10 calls | 4.8529ms | 92.21% | 246,927B |

원인은 정상 2001이 고빈도 필터를 우회해 `NetworkDebugStream.Add()`에서 reflection 기반 전체 payload 포맷팅과 레코드 생성을 수행하던 경로였다. `SubmitInput`은 같은 프레임에서 각각 0.0483ms, 0.0248ms였으므로 주 병목이 아니었다.

### 변경 내용

- 2001을 `PlayerMovement`로 정확히 분류했다.
- 정상 `Received` 2001의 상세 캡처는 전용 opt-in, 기본 OFF로 바꿨다.
- OFF일 때 `_formatter.Format()` 전에 반환한다.
- opt-in ON은 일반 고빈도 스위치로 다시 차단하지 않는다.
- `DeserializationFailed` 등 오류 기록은 전용 opt-in OFF에서도 보존한다.
- 실제 입력 `Publish()`와 SubmitInput, 입력 tick 규칙은 그대로 유지했다.

### 패치 전후 Development Profiler 수치

실행 길이와 처리량이 달라 완전히 동일한 A/B는 아니지만, 같은 Unity 6000.3.22f1 Development Player·호스트 Profiler 계열의 목적 지표가 일관되게 줄었다.

패치 후 느린 선택 행은 Pump 4.2430ms 중 Deserialize 포함 시간이 4.1282ms였다. 다만 Deserialize Self는 0.4941ms이므로, 그 내부의 새 수정 대상을 이 결과만으로 확정하지 않는다.

### Development 게스트 수치는 별도

Profiler 패치 전 실행에서 게스트 Update는 8.86/30.84/62.45회/s, 명령 생성은 31.78/38.22/47.88개/s였고 fallback은 48.26/37.85/21.37%였다. 패치 후 재캡처에서도 게스트별 Update는 53.97/24.27/7.76회/s, 명령 생성은 36.32/30.94/26.03개/s, fallback은 45.76/53.41/62.27%였다.

이는 한 PC에서 Development Player 4개와 Profiler를 함께 실행할 때 게스트 처리율이 크게 흔들린다는 자료다. **정상 2001 캡처 제거의 호스트 Pump 개선과 게스트 프레임 처리율 문제는 별개**이며, 이 값을 일반 빌드의 입력 회귀로 해석하지 않는다.

## 6. 두 PC 일반 빌드 기준선

초기·종료 구간을 제외한 207.087초 steady 구간 결과다.

| 지표 | 결과 |

| Held fallback | 47 |
| Neutral fallback | 20 |
| 전체 fallback | 67/12,426, 0.539% |
| 게스트 송신 실패 | 0 |

게스트의 새 고유 command 생성률 59.986/s와 호스트 권위 tick 60.004/s가 사실상 일치했다. Development/Profiler 실행에서 보였던 게스트 명령 공급 부족은 이 일반 빌드 2인 조건에서는 재현되지 않았다.

원격 표시 지표는 입력과 분리한다. 게스트가 보는 호스트는 보간 99.458%, 외삽 0.542%, 외삽 상한 0회였지만 도착 간격 최대 146.4ms와 일회성 외삽 증가가 있었다. 호스트가 보는 게스트는 현재 별도의 LateUpdate snapshot 보간 경로가 확인되지 않는다.

## 완료된 변경과 보존한 계약

### 완료·유지

- HostTick 기반 원격 렌더 시간축
- 최대 3틱 입력 backfill
- 호스트 `TickPreparing → ResolveTick` 로컬 입력 공급
- Jump/Fire edge의 pending·단일 소비 추적
- 새 Jump 명령의 조기 송신
- 2001 전용 수신 큐와 권위 pre-tick Pump
- Pump 처리량·대기·stale·fallback 저비용 집계
- Pump 내부 ProfilerMarker 계층
- 정상 2001 전체 payload 상세 캡처 기본 OFF
- 2001 역직렬화 실패 등 오류 기록 보존

### 변경하지 않은 계약

- 게스트 lead 계산
- ACK 기반 `lastResolvedTick + 12` 선행 상한
- 3틱 backfill 개수
- fallback held 시간과 edge 비복제 규칙
- CharacterMotor 이동·점프 수학
- wire payload와 서버 계약

## 아직 남은 항목

1. **호스트 게스트 표시 보간의 배포 설정**: 두 PC 2인 ON/OFF에서 표시 속도 표준편차 감소와 사용자 체감 개선을 확인했다. 보간 활성화와 1초 계측을 분리한 뒤 기본 ON 여부를 결정한다.
2. **일회성 snapshot 도착 지터**: 두 PC 실행에서 최대 도착 간격 146.4ms와 짧은 외삽 증가가 있었다.
3. **4인 일반 다중 PC 기준선**: 두 PC·1호스트+3게스트에서 호스트 60Hz 권위 틱과 세 Entity 표시 보간은 유지됐지만, 게스트 3중 실행 PC의 입력 소비율이 87.41~95.42%로 낮아졌다. 실제 네 PC 분산 성능과 입력 정확성 통과로 확대하지 않는다.
4. **ACK 상한에 붙는 짧은 burst**: 두 PC steady 구간 일부에서 Update와 command는 충분했지만 `clamped`가 몰린 창이 있었다. 전체 결과를 깨는 수준은 아니지만 잔여 0.539% fallback 분석 후보이다.
5. **종료·별도 서비스 오류**: NightEnd object timeout, UIRoot 정리 예외, Vivox timeout은 정상 플레이 입력 경로와 분리해 추적한다.
6. **호스트 자체 장시간 정지**: 권위 프로세스가 멈춘 동안 새 권위 snapshot을 만들 수 없는 구조적 한계는 남는다.

호스트 화면의 권위 게스트 표시 전용 위치 보간은 자동 회귀와 두 PC 2인 ON/OFF 실측을 통과했다. 일정 속도 선택 구간의 표시 속도 표준편차는 0.906m/s에서 0.355m/s로 감소했고, 비슷한 프레임 조건으로 제한해도 0.404m/s에서 0.350m/s로 개선 방향이 유지됐다. 다음 코드 수정 후보는 입력 lead·backfill·fallback이 아니라 **보간 활성화와 진단 계측의 분리**다.
